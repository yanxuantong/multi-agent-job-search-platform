第 14 章：Offline Eval：别靠感觉判断 Agent 有没有变好

Agent 质量不能只靠肉眼体验，必须有回归样例和可重复评估。

直接做实验 课程目录

这一章先解决什么问题

本项目的 eval suite 保护两类行为：结构化抽取是否正确，workflow trajectory 是否符合预期。

Eval 是 agent 系统的回归测试，不是一次性的 benchmark。每次改 prompt、模型、node、state schema，都应该跑 eval。

Deterministic eval 尤其适合早期：便宜、稳定、容易定位失败。

训练运动员不能只问教练「感觉怎么样」。你需要计时器、动作录像、固定测试项目。Agent eval 就是这些固定测试项目。

扩展工程手册：把这一章做成可执行练习

这章真正解决的问题

第 14 章关注的是 agent 系统的质量控制：当你改了 extractor、workflow、RAG、prompt 或 UI 后，怎样知道系统没有退化。这里的 eval 不是 Kaggle 式 benchmark，而是工程回归套件。

Datasetsamples/eval_suite.json 保存固定案例。每个 case 描述输入 JD、期望 company、期望 skills、期望 stop reason、最低 fit score。
Runnerjobagent/evals/runner.py 读取 suite，根据 eval_type 分派到 single-turn JD extraction 或完整 trajectory workflow。
System Under Testsingle-turn case 只跑 extract_jd()；trajectory case 跑 run_job_workflow()，因此会覆盖 graph、agents、HITL、fit score、state serialization。
Checks每个 case 产出一组 deterministic checks，例如 company 是否匹配、required skill 是否出现、stop_reason 是否正确、fit score 是否达标。
Reportrunner 汇总 total、passed、failed、pass_rate、by_type、failure_categories、results。CLI 和 tests 都复用这个结构。
Next Layer第 9 章新增 retrieval eval；未来还可以加 final-answer grounding、resume rubric、human-label calibration、LLM-as-judge。

代码解读：每个文件负责什么

samples/eval_suite.json

这是离线 eval dataset。它应该尽量接近你真实关心的岗位类型：AI engineer、FDE、RAG backend、agent observability、MCP tooling 等。新增功能时，先补 case，再改实现。

jobagent/evals/runner.py

主 eval runner。重点看它如何读 JSON、如何按 case type 分派、如何把 check 结果汇总成 pass/fail 和 failure category。

jobagent/evals/run_quality.py

单次 workflow 的质量门。它不是 dataset eval，而是产品运行后检查本次 run 是否生成了关键 artifact，例如 JD、fit analysis、resume proposal、tool audit。

jobagent/retrieval/eval_runner.py

RAG 专属 eval runner。它补上第 14 章的一个重要分支：除了 workflow trajectory，也要评估 retrieval trajectory。

tests/test_eval_runner.py

把 eval runner 自身纳入单测。它验证 failure categories、pass rate、case parsing 等逻辑，避免 eval 工具本身悄悄坏掉。

jobagent/cli.py

把 eval 暴露成可执行命令：eval 跑 workflow/JD suite，retrieval-eval 跑 RAG suite。面试展示时，CLI 是最直接的证据。

工程选择 Q&A

Q: Eval 应该覆盖最终输出还是中间轨迹？

A: 两者都要，但早期优先中间结构和 trajectory。因为它们稳定、便宜、可定位。最终输出质量要测，但最好建立在 typed artifact、retrieval context、tool audit 已经可靠的基础上。

Q: Deterministic checks 会不会太死板？

A: 对语义质量来说可能死板，但对 schema、路由、工具参数、stop reason、policy boundary 来说非常合适。AI 系统不是所有东西都要用 LLM judge。

Q: 什么时候引入 LLM-as-judge？

A: 当你要评估“答案是否充分”“语气是否适合”“是否忠实引用 retrieved context”这类开放问题时可以引入。但 judge prompt、judge model、抽样审计也要版本化，否则 judge 本身会漂。

Q: Eval suite 多大才有意义？

A: 初期 10-20 个高价值 case 就很有用，重点是覆盖真实风险：热门目标岗位、容易抽错的公司名、容易误判的技能、HITL 边界、RAG 证据命中。数量增长应该来自真实失败，而不是为了好看。

Q: Eval 是否应该进 CI？

A: 只要稳定、低成本、无外部凭证，就应该进。当前 deterministic suite 和 retrieval suite 都适合 CI；真实 LLM eval 可以先 nightly 或手动触发。

Q: Eval 失败后先改什么？

A: 先看 failure category，再看 trace/state。不要第一反应改 prompt。很多失败来自 extractor rule、state contract、retrieval source、stop reason 或 fixture 预期不清。

工程选择题：什么时候这样做，什么时候不要这样做

Eval case 应该覆盖最终输出还是中间轨迹？两者都要，早期先覆盖中间结构和 trajectory。 LLM-as-judge 是否必要？语义质量需要，但 deterministic rule 更适合 schema、工具参数、policy。 Eval 结果是否应该进 CI？只要稳定、低成本，就应该进。

这些问题比答案本身更重要。Multi-agent 工程的成熟度，不在于堆多少框架，而在于你能说清楚每个边界为什么存在、什么时候需要升级、升级会带来什么新复杂度。
