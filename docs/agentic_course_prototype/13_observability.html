第 13 章：Observability：Trace 是 Agent 系统的黑匣子

Agent debug 的第一原则：不要只看最终回答，要看轨迹。

直接做实验 课程目录

这一章先解决什么问题

本项目的 JsonlTracer 为每个 node 记录 span，包含 step、next_node、stop_reason 等 metadata。

真实 agent observability 还会记录 model generation、tool call、retrieval、guardrail、handoff、latency、token、cost、prompt version、eval score。

Trace 让你回答三个问题：系统看到了什么、做了什么、为什么停在这里。

飞机失事调查不能只看乘客最后一句话，要看黑匣子。Agent 系统也一样，最终输出只是结果，trace 才是过程证据。

扩展工程手册：把这一章做成可执行练习

这章真正解决的问题

第 13 章把 agent 从“看最终输出”推进到“看执行证据”。一个 multi-agent workflow 出错时，最终结果只告诉你它错了，trace 才告诉你它在哪里、为什么、用什么状态错了。

Run每次 workflow 都有 run_id，trace、checkpoint、web detail 都围绕同一个 run_id 聚合。
SpanJsonlTracer.span(node) 让每个 agent node 都产生 started_at、completed_at、status、metadata。
Metadataengine 会把 next_node、stop_reason、steps_used 等信息写进 span，形成可复盘的执行轨迹。
Exportlangfuse_exporter.py 说明本地 JSONL trace 如何映射到外部观测平台。
Productweb run detail 和 ops endpoints 使用这些证据，让用户和开发者都能知道系统当前状态。

代码解读：每个文件负责什么

jobagent/observability/tracer.py

本地 trace 核心。JsonlTracer 创建 span，TraceEvent 规定事件结构，_TraceSpan 在进入和退出节点时写 JSONL。

jobagent/graph/engine.py

调用 tracer 的地方。engine 不只调节点，还把节点结果转成 trace metadata，因此调度和观测是连在一起的。

jobagent/observability/langfuse_exporter.py

外部观测平台适配器。它把本地 trace event 转成 Langfuse observation，展示“本地先打证据，再接平台”的升级方式。

tests/test_learning_integrations.py

用 fake Langfuse client 测 exporter，不需要真实凭证。这个测试模式很适合学习外部 SDK integration。

.jobagent/runs/<run_id>/trace.jsonl

真实运行后的证据文件。调试时先看这里，而不是先猜 prompt 或 UI。

工程选择 Q&A

Q: log、metric、trace 谁最先做？

A: agent workflow 先做 trace。因为 agent 质量问题通常是路径问题：哪个节点看到了什么、调用了什么、为什么停下。

Q: 是否记录完整 prompt 和输出？

A: 开发期很有用，生产期要经过 redaction、retention 和 access control。求职产品里可能有简历、公司、个人经历，不能随便外发。

Q: 什么时候接 Langfuse 或 OpenTelemetry？

A: 当 trace 不只是给你本地 debug，而要支持 dashboard、团队排查、eval linkage、成本/延迟分析时，就值得接。

Q: Trace 和 eval 怎么配合？

A: eval 告诉你失败了，trace 告诉你失败路径。最好的 agent regression 报告应该能从 failed case 直接跳到 trace。

工程选择题：什么时候这样做，什么时候不要这样做

日志、metric、trace 谁最重要？agent debugging 首先需要 trace，因为它保留因果路径。 是否记录完整 prompt/output？开发阶段有用，生产环境要考虑 PII、secret、redaction。 Trace 是否要接 OpenTelemetry？如果已有 infra observability 栈，应该考虑统一 schema。

这些问题比答案本身更重要。Multi-agent 工程的成熟度，不在于堆多少框架，而在于你能说清楚每个边界为什么存在、什么时候需要升级、升级会带来什么新复杂度。
