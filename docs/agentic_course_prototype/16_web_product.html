直接做实验 课程目录

这一章先解决什么问题

JobAgent 的 web surface 把 workflow 变成一个可操作 cockpit：提交 JD、查看 run、审批 proposal、继续流程、查看结果。

Agent UI 最重要的是状态可见：现在在哪个 node、为什么暂停、需要用户做什么、输出是否最终生效。

这也是 portfolio 价值所在：不仅有后端 workflow，还有用户能理解的产品表面。

一个好机场不是只让飞机飞，它还要让乘客知道登机口、延误原因、安检状态和下一步动作。Agent UI 也是信息机场。

扩展工程手册：把这一章做成可执行练习

这章真正解决的问题

第 16 章把 agent workflow 从脚本变成产品。对求职平台来说，UI 的价值不是好看而已，而是让用户理解系统现在做到哪里、需要他们批准什么、哪些输出已经可以信任。

Homeindex.html 是 command center：提交 JD、查看 workflow strip、理解 bounded agents。
Create RunPOST /runs 校验输入、通过 guardrail、创建 workflow run，并写入 store/checkpoint。
Review Gateresume proposal 生成后进入 approval 状态，UI 展示 proposal 和风险，让人类决定是否继续。
Run Detailrun.html 展示 artifacts、trace rows、retrieval evidence、tool audit 和最终结果。
Ops/healthz、/readyz、/ops/status 让部署环境能判断服务状态。

代码解读：每个文件负责什么

jobagent/web/app.py

FastAPI product shell。它连接表单、store、workflow、approval、ops endpoint 和模板渲染，是产品化的中枢。

jobagent/web/store.py

run store 抽象。LocalRunStore 适合本地/公开 demo；PostgresRunStore 是 durable state 的升级边界。

jobagent/web/templates/index.html

首页产品体验。它应该让用户不用懂内部代码也能开始一次 job-agent run。

jobagent/web/templates/run.html

run detail 页面。这里最能体现 agent product 与普通表单的差异：状态、审批、证据、trace、RAG context 都在同一页。

jobagent/web/static/app.css

产品 UI 的视觉系统。它不仅管颜色，还影响信息密度、卡片层级、移动端可读性和审批区域的清晰度。

工程选择 Q&A

Q: Agent UI 应该是聊天框还是 cockpit？

A: JobAgent 更适合 cockpit。它是有阶段、有审批、有证据链的 workflow，用户关心状态和决策点，不只是自由聊天。

Q: 中间结果要不要展示？

A: 要展示能帮助用户判断的中间结果：fit concerns、resume proposal、RAG evidence、trace summary。不要把所有内部字段都塞进页面。

Q: 错误提示怎么分层？

A: UI 给用户可行动的错误，trace/log 给开发者技术细节。两者应该由同一 run_id 连接起来。

Q: 为什么 portfolio 需要 UI？

A: 因为 FDE/AI engineer 不只是写 workflow，还要把复杂系统交到用户手里。UI 是你理解产品边界的证据。

工程选择题：什么时候这样做，什么时候不要这样做

Agent UI 应该像聊天框还是 cockpit？本项目更适合 cockpit，因为 workflow 状态比对话本身更重要。 是否展示中间结果？应展示对用户决策有帮助的中间结果，同时避免信息过载。 错误提示应该技术化还是用户化？UI 用户化，trace/log 技术化。

这些问题比答案本身更重要。Multi-agent 工程的成熟度，不在于堆多少框架，而在于你能说清楚每个边界为什么存在、什么时候需要升级、升级会带来什么新复杂度。
