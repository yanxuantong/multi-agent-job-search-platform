第 19 章：调试一本 Agent 系统：从现象回到 state、trace、node

Agent debug 不应该从改 prompt 开始，而应该从证据链开始。

直接做实验 课程目录

这一章先解决什么问题

一个系统输出奇怪结果时，先判断问题发生在输入、guardrail、state、node、tool、checkpoint、trace、UI 还是 eval 覆盖。

本项目适合建立一套可复用 debug playbook：CLI 复现、检查 checkpoint、阅读 trace、定位 node contract、补 eval case、再改实现。

这会训练真正的 agent engineering 手感：少猜，多看证据。

医生不会一上来就开药。他会问症状、量体温、看化验单、查病史。Agent debug 也一样，prompt 只是最后可能调整的治疗方案之一。

扩展工程手册：把这一章做成可执行练习

这章真正解决的问题

第 19 章给你一套 debug playbook：agent 系统出错时，不要第一反应改 prompt，而是沿着 input、state、checkpoint、trace、node、eval、UI 的证据链逐步缩小范围。

Reproduce先用 CLI 或 web run 复现问题，固定输入和 run_id。
Checkpoint检查 .jobagent/checkpoints，确认 typed state 是否已经错误。
Trace检查 .jobagent/runs 的 JSONL，确认哪个 node 停下、下一步是什么、有没有异常。
Node Contract如果 state 错，回到对应 agent 文件；如果 state 对但 UI 错，再看 template/helper。
Regression补 eval 或 unit test，再修实现。不要只靠手动刷新页面确认。

代码解读：每个文件负责什么

jobagent/graph/engine.py

调度证据源。预算、未知节点、stop_reason、pending_node、trace metadata 都在这里形成。

jobagent/storage/checkpoint.py

状态快照入口。它让你能判断 bug 是否已经写进 state，还是只是展示层问题。

jobagent/observability/tracer.py

时间线证据。trace 适合判断执行顺序、节点耗时、异常和暂停原因。

jobagent/evals/runner.py

回归保护。发现 bug 后，如果能写成 eval case，就应该先把失败固定下来。

tests/

更小粒度的保护网。UI bug、guardrail bug、store bug、retrieval bug 不一定都放进大 eval，很多更适合 unit test。

动手实验：按顺序执行

实验 1：从 run_id 找证据

.venv/bin/python -m jobagent.cli demo --auto-approve
ls -t .jobagent/checkpoints | head
find .jobagent/runs -name trace.jsonl -print | sort | tail -1

目标：把一次运行对应的 checkpoint 和 trace 找出来。

实验 2：读 checkpoint 和 trace

latest_checkpoint=$(ls -t .jobagent/checkpoints/*.json | head -1)
python3 -m json.tool "$latest_checkpoint" | sed -n '1,120p'
latest_trace=$(find .jobagent/runs -name trace.jsonl -print | sort | tail -1)
sed -n '1,80p' "$latest_trace"

目标：练习判断问题是在 state artifact、node route，还是展示层。

实验 3：用 eval 锁住失败

sed -n '1,180p' samples/eval_suite.json
sed -n '1,220p' jobagent/evals/runner.py

目标：学会在修 bug 前设计一个最小失败 case。

工程选择 Q&A

Q: 什么时候才改 prompt？

A: 当 input、retrieval、state、tool、guardrail、UI 都证明没问题，而语义质量仍然不足时。prompt 是候选原因，不是默认原因。

Q: trace 太多怎么办？

A: 本地学习可以保留较多；生产要按 run_id、user、时间窗口检索，并设置 retention、redaction 和采样策略。

Q: checkpoint 和 trace 哪个先看？

A: 输出内容错，先看 checkpoint；执行路径错，先看 trace。两者最终要结合。

Q: 自动 retry 是不是好事？

A: 只有幂等、低风险、可观察的失败才适合 retry。外部写入和审批动作不能随便自动重放。
