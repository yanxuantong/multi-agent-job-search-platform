每个升级都按同一结构分析：当前痛点、升级收益、新复杂度、JobAgent 落点、验证方式。

扩展工程手册：把这一章做成可执行练习

这章真正解决的问题

第 20 章把“我知道很多技术名词”变成“我知道什么时候引入它们”。对 AI infra 来说，成熟度不是堆栈越满越好，而是每个升级都有触发条件、复杂度预算和验证方式。

Inventoryintegrations/registry.py 列出本项目的学习型 integration：LangGraph、LLM providers、Langfuse、Postgres/pgvector、MCP、Docker/Render。
Trigger每个升级项都应该由痛点触发：durability、semantic retrieval、tool reuse、observability、model quality、deployment scale。
Complexity升级会带来依赖、凭证、迁移、成本、故障模式和测试矩阵。
Boundary用 provider、store、retriever、exporter、MCP server 等边界把升级限制在可替换位置。
Verification每次升级都必须有保持不变的 eval/test：trajectory、retrieval hit、web route 或 exporter contract。

代码解读：每个文件负责什么

jobagent/integrations/registry.py

技术栈目录。它适合用来复盘每个 integration 的状态、学习目的和 adoption trigger。

pyproject.toml

依赖边界。看 optional dependency 和测试配置，能判断哪些能力是默认路径，哪些是可选增强。

jobagent/storage/postgres_memory.py

Postgres/pgvector 方向的雏形。它代表 memory/retrieval 从本地 JSON 走向 durable query layer。

mcp_server/

MCP-shaped 工具边界。它适合当工具需要跨客户端复用，而不是只在本项目内部调用时升级。

tests/test_learning_integrations.py

integration contract 测试。它展示如何在不依赖真实云服务的情况下验证 adapter 行为。

工程选择 Q&A

Q: 什么时候引入 LangGraph？

A: 当本地 engine 开始复制 durable execution、interrupt、复杂 routing、streaming、checkpoint 可视化时。

Q: 什么时候引入 pgvector？

A: 当 corpus 变大、同义词/语义匹配明显影响 recall、需要跨文档检索，且你已有 retrieval eval 能证明升级收益时。

Q: 什么时候接真实 LLM provider？

A: 当 deterministic baseline 已经稳定，而写作质量、语义判断或开放推理成为瓶颈时。接入前先有成本、超时、重试、structured output 失败策略。

Q: 什么时候做 MCP？

A: 当工具要被多个客户端或 agent runtime 复用，或者你希望把 capability 明确暴露成协议资源时。

行业脉搏：把本章放到 2026 AI infra 里看

2026 的 agent stack 趋势是组合式：runtime、protocol、observability、eval、deployment、identity 分别由不同工具覆盖。

未来的 AI infra 工程师要能在 OpenAI Agents SDK、LangGraph、MCP、Langfuse、OpenTelemetry、AWS AgentCore、Google A2A 等之间做边界判断。

读这些链接时，不要只记产品名。更重要的是把它们映射回本项目：哪些能力已经在 JobAgent 里有教学版，哪些能力属于未来的生产升级。
